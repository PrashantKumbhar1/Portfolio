# SEO maintenance

## Routine workflow

Keep the design stable. Edit factual content, run the checks, review the local production preview, then deploy only when authorized. On Windows use `npm.cmd` if PowerShell blocks npm.ps1.

```
npm run check
npm run test:portfolio
npm run build
npm run seo:preview
# In another terminal:
npm run seo:check -- --url http://127.0.0.1:5174
```

The build runs the SEO checks automatically; `seo:check` can also rerun them against current output. Production artifacts live in `client/dist`, not root `dist`. `seo:preview` runs a small local server with the generated route/header behavior. Vite preview uses its own SPA fallback and cannot prove Netlify 404 behavior. Actual deployment validation is still required:

```
npm run seo:check -- --url https://prashantkumbhar.netlify.app
```

Only use that command after deploying the matching build. It performs public read-only requests, not a Search Console submission or email send. It should fail on old deployments or broken crawl/routing metadata. For a preview-context build, keep the same CONTEXT when rerunning checks. Preview artifacts must not be reused for production.

## Metadata and crawl files

Edit title, description, preferred homepage URL and share image in `script/seo-config.mjs`. Keep one head writer and one canonical. Vite inserts the metadata into the source template, then the prerender step inserts JSON-LD from repository identity data. Do not add dynamic duplicate meta writers or override social URLs from staging hostnames. Keep `lang=en`, unrestricted viewport zoom, and the real Google verification token in `client/index.html`.

Robots, sitemap, 404, `_headers` and `_redirects` are generated by `script/prerender.mjs`; edit their generator rather than ignored build files. The sitemap intentionally has one URL and no lastmod. Add a URL only after creating a real, useful canonical page, rendering it and verifying successful HTTP responses, navigation and unique metadata. A fragment, filter, modal, query or nonexistent case route does not belong in the sitemap. If genuine routes are added, update server routing, generation and tests together.

The generated preview noindex header/meta discourages indexing but does not protect private information. Netlify HSTS is already provided; test any future CSP with actual Google Fonts, inline presentation and EmailJS requests before enforcement. Do not cache HTML immutably or clear revalidation without a reason. Fingerprinted assets can retain immutable caching.

## Projects and identity

Edit structured project data in `client/src/portfolio/data.ts`. Keep development status accurate and summaries concrete. Add problem, actual technical approach, tools, limitations and verified outcomes. Do not invent detection rates, production users, employers, certifications or repositories. Only add project demo/repository links when their exact public URL is known and tested. Existing project modals remain interaction views, not separate indexable pages. The current GitHub button intentionally links to the verified profile.

Maintain logical headings and descriptive button/link names. Keep one visible homepage H1. Every added image needs accurate alt text and dimensions. Decorative diagrams stay aria-hidden where appropriate; interactive diagrams retain accessible controls. Do not add hidden keyword blocks. Retest keyboard focus, dialogs, search, mobile horizontal scrolling, models, Resume download and contact validation after related edits.

## Images and fonts

Original `profile.png` must remain untouched and uncropped. The WebP files are derived assets. If replacing the portrait with an authorized new source, regenerate all four variants at the same aspect ratio, update dimensions if necessary, check visual quality and ensure the lossless full-size file matches. Keep picture srcset and the responsive preload in sync. Do not lazy-load the hero portrait; below-fold logos can remain lazy. The branded social JPEG is 1200 x 630 and should only be replaced for a real branding change. Current fonts use display=swap; changes need CLS/visual testing rather than score speculation.

## Monitoring and manual checks

After each authorized deployment, inspect raw HTML, robots/sitemap, unknown-path status, canonical redirect, lazy chunks and asset headers. Run Google/Schema validators; then use Search Console URL Inspection and Sitemaps. Do not treat a successful local build as proof of indexing or field Core Web Vitals. Compare Search Console data over comparable periods. Record actual Lighthouse mobile/desktop runs with URL, date, browser/tool version, throttling conditions and raw reports when available. Avoid promising 90+ scores or good field metrics without data.

Before claiming release-ready interaction checks, test a real desktop and narrow mobile viewport, including the carousel arrows/swipe and 3D controls, keyboard search, each case-study tab, map filters, Resume, validation errors, and a single authorized email send/inbox check. Check the browser console for hydration/chunk errors. Reduced-motion must keep content usable. External platforms may block automated profile checks; report those as unverified rather than broken links.

No secrets belong in Vite variables. EmailJS public identifiers are browser configuration; private account keys, Google tokens and passwords must not be committed.

## Release artifact and raw response checks

With `npm run seo:preview` running, execute `python script/verify-release-html.py` to parse the initial HTTP body without JavaScript. After preparing the ZIP, run `python script/verify-release-artifact.py`; it must match every current `client/dist` file and reject stale or source-root archives. These scripts require Python 3, use only the standard library and do not upload anything. See `SEO_RELEASE_CHECKLIST.md` for pending browser checks and exact Lighthouse commands.
